```plaintext
## 5. 核心業務邏輯 (Core Business Logic)

### 5.1 錨點日期演算法 (Anchor Date Algorithm)
[cite_start]為確保大小月切換公平性，定義首次付費日為 **Anchor Day** [cite: 88]。
* 計算公式：
    > [cite_start]Next Month = 當前日期 + 1 個月 [cite: 90]
    > [cite_start]Target Day = Min(Anchor Day, Next Month 的最後一天) [cite: 91]

### 5.2 觀眾投稿與金流流程
1. [cite_start]**身份選擇**：預設匿名或點擊驗證 Twitch/YT 會員 [cite: 97, 98]。
2. [cite_start]**AI 預審**：系統送至 OpenAI 偵測惡意內容，通過才發放 `validation_token` 並進入付款 [cite: 101, 103]。
3. [cite_start]**金流處理**：完成付款後透過 Webhook 更新狀態、增加點數、進入收件匣 [cite: 106]。
4. [cite_start]**退款機制**：若直播主移除留言，系統呼叫 Recur API 執行退款並更新點數 [cite: 111, 113]。

## 6. 前端工程論點 (Front-end Engineer Perspectives)

身為前端工程師，針對本專案的 **Nuxt 3 + TailwindCSS** 架構，額外提出以下前瞻性建議：

* **Serverless 效能優化 (Edge Side Rendering)**：
    [cite_start]由於採用 Vercel/Netlify 環境 [cite: 23]，應充分利用 Nuxt 的 Nitro 引擎，將驗證與 AI 預審邏輯部署在 Edge Network，以降低全球观众投稿時的延遲。
* **即時性替代方案 (Optimistic UI & Polling)**：
    [cite_start]規格中不使用長連線 WebSocket [cite: 23]。
    > * 直播主後台：應實作 **Optimistic UI**，在操作「移除」或「投放」時立即更新介面狀態。
    > [cite_start]* OBS Overlay：使用 **SWR (Stale-While-Revalidate)** 策略進行 3-5 秒的 Polling [cite: 139]，確保動效平滑且不因短暫斷線崩潰。
* **型別安全 (End-to-End Type Safety)**：
    利用 Drizzle ORM 生成的 Schema 直接共享給 Nuxt Server 與 Client 端，確保從資料庫到前端 UI 的 TypeScript 型別一致性，減少 AI 欄位解析出錯的風險。

---

## 7. 風險與限制

* [cite_start]**金流自動化**：需確認 Recur/TapPay 支援全自動退款，否則需建立人工退款佇列 [cite: 143]。
* [cite_start]**執行超時**：Serverless 環境需注意 AI 分析或 Webhook 可能超過 10s-60s 的限制 [cite: 144]。
* [cite_start]**並發與配額**：點數扣除需使用 DB Transaction；第三方平台 API 查詢需實作快取 (Cache) 機制 [cite: 145, 146]。
```
